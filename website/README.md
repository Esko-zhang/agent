# Durlevel 外贸独立站

按需求 Excel（`首页` / `产品列表页` / `联系我们`）实现的**登录制**产品展示站：
公司产品目录 + 业务员联系方式，配套中文管理后台。

设计方案见 [`docs/规划方案.md`](docs/规划方案.md)。

## 在自己电脑上预览（约 5 分钟）

需要先装 [Node.js](https://nodejs.org/)（选 LTS 版，一路下一步即可），然后打开终端
（Windows：开始菜单搜 `PowerShell`；Mac：搜 `终端`），逐行粘贴：

```bash
git clone -b claude/adoring-shannon-88sms1 https://github.com/Esko-zhang/agent.git
cd agent/website
npm ci                                  # 安装依赖
ADMIN_PASSWORD=Preview123 npm run init-db   # 建库，并把管理员密码设为 Preview123
npm run seed-demo                       # 填入演示产品和业务员，便于查看效果
npm start
```

Windows PowerShell 的第 4 行要改成两句：

```powershell
$env:ADMIN_PASSWORD="Preview123"
npm run init-db
```

然后浏览器打开 **http://localhost:3000** ，用 `admin` / `Preview123` 登录。

- 产品列表：<http://localhost:3000/products>
- 联系我们：<http://localhost:3000/contact>
- 管理后台：<http://localhost:3000/admin>

停止运行按 `Ctrl + C`。换个端口用 `PORT=8080 npm start`。

> 演示数据只是为了看效果，正式使用前先清掉：`node scripts/seed-demo.js --clear`

## 功能一览

**前台（英文，面向海外客户）**
- `/` 登录页 —— 即首页，Logo + 登录账号 + 登录密码，**无自助注册入口**
- `/products` 产品列表 —— 品牌 Logo、搜索框、三个分类锚点导航，三个区块各有独立表头：
  | 区块 | 字段 |
  |---|---|
  | OEM成品 | No. / 产品图片 / 产品英文名字 / 剂型 / 规格 / 产品标签 / 备注 |
  | 提取物 | No. / 产品图片 / 产品英文名字 / 含量 / 比例 / 备注 |
  | 食品添加剂 | No. / 产品图片 / 产品英文名字 / 剂型 / CAS号 / 备注 |
- `/contact` 联系我们 —— 业务员名片（照片 / 姓名 / 电话 / WhatsApp / 邮箱），WhatsApp 自动生成 `wa.me` 链接
- `/inquiry` 询盘单 —— 客户把产品加进来，填数量和需求后提交

**后台（中文，`/admin`，仅管理员和业务员可进）**
- 产品管理：增删改、图片上传、排序、上下架；表单按所选分类自动切换字段
- **批量导入**：Excel / CSV 导入产品，先预览再确认
- **询盘管理**：客户询盘收件箱，状态流转、指派业务员、内部备注
- **客户意向**：按账号汇总搜索、文档下载和询盘，算出意向分
- 业务员管理：增删改、照片上传、排序、显示/隐藏
- 账号管理：创建账号、改密、设角色（管理员/用户）、停用、删除
- 网站设置：Logo、品牌名、各页文案、三个区块标题、页脚、访问记录时区与保留期
- **访问记录**：谁、什么 IP、什么时间进了网站
- **联系方式汇总**（**仅管理员**）：所有账号的邮箱、电话、WhatsApp、国家一张表，可导出 CSV

## 账号与权限

三种角色，账号只能自上而下发放，前台没有注册入口：

| 角色 | 可进后台 | 可发放的账号 | 可用板块 |
|---|---|---|---|
| **管理员** | ✓ | 业务员、用户 | 全部（含**仅管理员可见**的「联系方式汇总」） |
| **业务员** | ✓ | 仅用户 | 概览、询盘管理、账号管理、客户意向、访问记录（**均只限自己的客户**） |
| **用户** | ✗ | — | 仅前台产品与联系页 |

- **「管理后台」按钮对用户账号根本不渲染**，不是靠隐藏；即使手敲 `/admin` 的网址也会被挡（403）。
- 业务员**各管各的客户**：只看得到、也只能操作**自己创建的**用户账号。其他业务员的客户、以及管理员和业务员账号，都不显示也动不了。
  这条隔离贯穿四处——账号管理、询盘管理、客户意向、访问记录，直接敲 URL 打开别人的客户也会被挡（403）。管理员看得到全部。
- 业务员无法把任何账号设为管理员或业务员——即便伪造表单提交，角色也会被强制落为「用户」。
- 系统始终保留至少一个启用的管理员；谁都不能停用或删除自己。
- **每个账号都会记录是谁创建的**（`created_by`）。这条归属关系同时决定两件事：客户在询盘页看到哪位业务员的 WhatsApp，以及哪位业务员能管理这个客户。
- 创建业务员账号时，管理员可以把它**关联一张「业务员名片」**——名片上的 WhatsApp 就是客户看到的号码。

> 注意区分两个「业务员」：后台的**「账号管理」**管的是能登录的账号；
> **「业务员名片」**管的是「联系我们」页上展示的联系人卡片，它不需要登录，两者互不影响。

## WhatsApp 询盘

客户打开询盘页，顶部会显示**创建他账号的那位业务员**，带两个按钮：

- **Chat on WhatsApp** —— 直接聊天；
- **Send this list on WhatsApp** —— 打开 WhatsApp 时**消息已经写好**，包含产品清单、数量和备注。

```
Hello, this is Nordic AB.
I would like a quotation for:

1. Vitamin C 1000mg Tablets — Qty: 500 kg — food grade
2. Collagen Peptide Gummies — Qty: 2000 bottles

Account: buyer10
```

链接在服务端生成（没有 JS 也能用），同时 `public/js/inquiry.js` 会在客户边填数量时**实时更新**消息内容。

**号码从哪来**：客户账号 → `created_by` 指向的业务员账号 → 该账号关联的「业务员名片」→ 名片上的 WhatsApp。
任一环节缺失时（例如账号是管理员直接创建的、或业务员还没关联名片），自动退回到第一个填了 WhatsApp 的在岗名片，按钮不会变成死链。

## 询盘（RFQ）

客户在产品列表页每行点「+ Inquiry」把产品加进询盘单，到 `/inquiry` 填数量、备注和联系方式后提交。
提交后：

1. 询盘存入数据库，出现在后台「询盘管理」，侧边栏带未处理数量角标；
2. 后台可改状态（待处理 / 已跟进 / 已关闭）、指派业务员、写内部备注；
3. 记一条「提交询盘」到访问记录，并计入客户意向分；
4. 如果配了 SMTP，给在岗业务员的邮箱发一封通知。

询盘单存在**签名 Cookie** 里（最多 50 个产品，7 天有效），不占数据库，换浏览器会清空。
询盘的产品名称和分类在提交时会**拷贝一份**存下来，之后改名或删除产品都不影响历史询盘。

### 邮件通知（可选）

不配也能用——询盘照样保存，只是不发邮件。收件人默认是所有「显示中」业务员名片上的邮箱，
也可以用 `INQUIRY_NOTIFY_TO` 额外指定（逗号分隔）。
**发信失败只记日志，不会导致客户看到报错**——询盘已经存下来了。

`.env.example` 里已按**阿里云企业邮箱**填好默认值：

```
SMTP_HOST=smtp.qiye.aliyun.com
SMTP_PORT=465
SMTP_SECURE=1
SMTP_USER=sales@你们的域名
SMTP_PASS=三方客户端安全密码
SMTP_FROM=Durlevel <sales@你们的域名>
```

阿里云这边有三个坑，三个都踩过才会通：

1. **管理员要先给这个账号开「SMTP 服务 / 三方客户端」**——较新开通的租户默认是关的，
   不开的话密码再对也是 `535 authentication failed`。
2. **`SMTP_PASS` 填「三方客户端安全密码」**，在邮箱设置 → 账户安全里生成，不是网页版登录密码。
3. **`SMTP_FROM` 必须和 `SMTP_USER` 是同一个地址**（带显示名可以），换个地址发会被拒。

端口用 465 + SSL 而不是 25：**阿里云 ECS 默认封禁 25 端口出站**。安全组也要放行 465 出站。
域名的 SPF 记录应包含 `include:spf.qiye.aliyun.com`，否则对方可能按 SPF 退信。

### 验证：`npm run mail-test`

```bash
npm run mail-test                  # 发给业务员名片上的邮箱
npm run mail-test -- you@x.com     # 只发给指定地址
npm run mail-test -- --check       # 只验证连接和登录，不发信
```

它先打印当前配置（密码只显示位数），再连接登录，最后发一封测试邮件。
失败时不只给 SMTP 原文，还会直接指出该去改哪里——登录被拒、端口被挡、SPF 退信、
发件人地址不符，各有各的提示。

## 产品文档（TDS / COA / MSDS）

在后台「产品管理 → 编辑某产品」页面底部上传，支持 PDF / Word / Excel / 图片，单个默认上限 20MB。
客户登录后在产品列表页的 Documents 列看到标签（TDS、COA…）并下载。

**文档存在 `data/docs/`，不在 `public/` 下面**，只能通过 `/docs/:id` 这个需要登录的路由拿到，
每次下载都会记入访问记录（带产品名和文档标签），并计入客户意向分。

> 产品**图片**仍在 `public/uploads/` 下，文件名是 32 位随机串，知道地址的人不登录也能打开。
> 图片一般无所谓；真正敏感的规格数据请放进文档，走上面的受控通道。

## 批量导入产品

后台「产品管理 → 批量导入」。先下载模板（含表头、三个分类的示例行和一页填写说明），
填好后上传 `.xlsx` / `.xls` / `.csv`，系统会先给出**预览**：哪些新增、哪些更新、哪些有问题，
确认后才真正写入（整批在一个事务里）。

- 表头中英文都认（`分类`/`category`、`产品英文名字`/`product name` 等）；
- 用 **分类 + 产品英文名字** 识别产品：已存在就更新，不存在就新增；
- 有问题的行（分类无法识别、缺名字、文件内重复）会被单独列出并跳过，不影响其他行；
- 图片和文档无法通过表格导入，需在后台逐个上传；
- 预览结果 30 分钟内有效，且只能确认一次。

## 客户意向

后台「客户意向」把访问记录和询盘揉成一张「该先给谁打电话」的表。

产品列表是一整页，所以「打开了页面」说明不了客户关心哪个产品。真正有意义的信号是：

| 信号 | 权重 | 含义 |
|---|---|---|
| 提交询盘 | 20 / 次 | 最强，已经开口要报价 |
| 下载文档 | 6 / 次 | 采购前通常先要 TDS / COA |
| 使用搜索 | 2 / 次 | 客户自己说出口的需求 |
| 浏览页面 | 1 / 次（上限 40） | 最弱，只说明来过 |

点进某个账号可以看到：询过价的产品、下载过的文档、搜索过的关键词、历史询盘、用过的 IP 和最近活动。

## 访问记录

后台「访问记录」页回答一件事：**谁、从哪个 IP、在什么时间进了网站。**

记录四类事件：

### 谁看得到哪些记录

| | 管理员 | 业务员 |
|---|---|---|
| 自己客户的记录 | ✓ | ✓ |
| 其他业务员客户的记录 | ✓ | ✗ |
| 业务员和管理员自己的记录 | ✓ | ✗ |
| 针对**未知账号**的登录尝试 | ✓ | ✗ |

业务员看得到**自己客户被撞密码**的失败记录（登录失败按输入的账号归属），
但看不到针对不存在账号的扫描——那属于全站安全信息，只有管理员需要。

统计数字、账号下拉、国家下拉和 CSV 导出都按同一范围收窄，所以业务员看到的
「共 N 条」与他实际能打开的记录一致。范围在服务端先于一切用户输入应用，
手动在网址里塞 `?username=别人的客户` 也拿不到数据。

### 国家 / 地区

每条记录会**按 IP 推算来访国家**，列表里显示国旗 + 中文国名，可按国家筛选，CSV 导出也带这一列。

用的是 `ip3country`（约 0.5MB 的离线库）：**没有 API key，不发任何网络请求，客户 IP 不会离开你们的服务器**——
这点在 IP 属于个人数据的前提下很重要。两个已知限制，都会显示「未知」而不是给错答案：

- 只支持 IPv4，IPv6 访客查不到；
- 挂 VPN 或代理的访客，显示的是出口节点所在国。

国家在**写入日志时就算好存下来**，所以以后更新 IP 库也不会改写历史记录。
同样地，`TRUST_PROXY` 配错会让所有 IP 变成代理地址，国家也就跟着全错——见上面的表格。

| 事件 | 何时记录 |
|---|---|
| 登录成功 | 账号密码正确 |
| 登录失败 | 密码错、账号不存在、账号被停用、触发限流 |
| 退出登录 | 用户主动退出 |
| 浏览页面 | 已登录用户每打开一个页面 |
| 下载文档 | 下载某个产品的 TDS / COA 等 |
| 提交询盘 | 提交一份询盘 |

每条记录：时间、账号、角色、事件、页面地址、IP、浏览器标识。
支持按账号 / 事件类型 / 日期区间 / 关键词（IP、页面、浏览器）筛选，分页浏览，一键导出 CSV（UTF-8 带 BOM，Excel 直接打开不乱码）。

**不记录的**：静态资源（图片、CSS）、健康检查、404，以及未登录访客打开登录页——否则扫描机器人会把日志刷满。失败的登录尝试一定会记，这正是要盯的安全信号。

### ⚠️ 必须配置 `TRUST_PROXY`，否则 IP 全是错的

应用拿到的「客户端 IP」取决于它信任几层代理。配错会让这个功能完全失效：

| 部署方式 | `TRUST_PROXY` | 不配会怎样 |
|---|---|---|
| 直接暴露端口（不推荐） | `0` | — |
| Nginx / Caddy 反代 | `1` | 每条记录都是 `127.0.0.1` |
| Cloudflare 等 CDN → Nginx | `2` | 每条记录都是 Nginx 的内网 IP |
| 更多层 | 层数，或填代理 IP / 网段 | 同上 |

数字设得过大也危险：访客可以自己发 `X-Forwarded-For` 头伪造 IP。**按实际层数填**。

### 隐私合规

IP 属于个人数据。客户在欧盟 / 英国时 GDPR 适用，要求有保留期限并在网站上告知。因此：

- 日志默认保留 **180 天**，超期每天自动清理（后台「网站设置」可改）；
- 请在网站上写一句隐私说明，告知会记录访问日志及保留多久；
- 仅在排查问题或安全审计时查阅。

时间默认按 `Asia/Shanghai` 显示，可在「网站设置」改成任意 IANA 时区。

## 联系方式汇总（仅管理员）

后台「联系方式汇总」把**所有账号的有效联系方式**摆成一张表：登录账号、公司、姓名、
邮箱、电话、WhatsApp、国家/地区、所属业务员、询盘次数、最近登录。

**只有管理员看得到。** 业务员进不去——这一页的意义就是跨业务员看全盘，而业务员自己的
客户本来就在「账号管理」里，且可编辑。手敲 `/admin/contacts` 会被挡（403），
`/admin/contacts/export.csv` 同样挡掉，侧边栏对业务员根本不渲染这一项。

### 联系方式从哪来

同一个客户的联系方式散在三个地方，哪个都不完整，所以这一页把它们合并，**并标出每个值的来源**：

| 标签 | 来源 | 说明 |
|---|---|---|
| **已存** | 账号本身 | 在「账号管理」里填的，或一键回填进来的。最准，永远优先 |
| **询盘** | 客户自己填的询盘单 | 取**最近一次非空**的值；某字段最近一次没填，就往前找 |
| **名片** | 业务员名片 | 业务员账号关联的名片上的邮箱 / 电话 / WhatsApp |
| **IP** | 访问记录 | 按访问 IP 推算的国家，**只用于兜底国家**，不会用来猜电话或邮箱 |

### 一键回填

客户在询盘单上填过、但账号记录里还空着的字段，可以一键补上——整页一个按钮，
也可以逐行补。**已有的值永远不会被覆盖**，所以人工核实过的号码不会被客户随手填的覆盖掉。

### 国家统一成国家代码

填写时输入框带 249 个国家/地区的下拉建议，中英文、两位代码（`US`、`BD`）都认，
`USA`、`UK`、`Holland`、`中国大陆`、`Türkiye` 这类常见写法也认。
存进库的统一是 ISO 两位代码，所以能按国家筛选、能显示国旗 + 中文国名。
**认不出来的写法会直接报错**，不会悄悄丢掉。

### 填写入口只有一个

要改某个账号的联系方式，去**「账号管理」**——每行「填写 / 修改」展开就是那五个字段。
业务员也能在那里维护**自己客户**的联系方式（管不到别人的客户）。
汇总页只读 + 回填 + 导出，不做第二套编辑入口，省得两边不一致。

### 筛选与导出

按角色、国家/地区、「有/无联系方式」「有可回填的询盘信息」筛选，或用关键词搜
账号 / 姓名 / 公司 / 邮箱 / 电话 / 国家 / 业务员。
国家关键词按代码匹配，所以搜 `UAE`、`阿联酋`、`AE` 结果相同。
CSV 导出带 UTF-8 BOM（Excel 直接打开不乱码），每个值后面跟一列「来源」，
以 `+` 开头的号码会加前导撇号，Excel 不会当成公式。

## 页面高度（自适应）

页面**正好铺满一屏**，不论是笔记本、27 寸大屏还是手机；内容超过一屏时才自然变长。
用的是 `--page-min-height: 100dvh`（不支持 dvh 的浏览器回落到 `100vh`）。

`dvh` 而不是 `vh`，是因为手机浏览器的地址栏会收起展开：用 `vh` 会导致页面比可视区域高一截，
出现没必要的滚动条。

- 页面是 flex 纵向布局，页脚落在屏幕底边，不会悬在半空；
- 登录卡片在屏幕正中；屏幕高度不足 640px 时自动收紧内边距，保证整张卡放得下；
- 后台侧边栏 `position: sticky`，长页面滚动时导航和「退出登录」始终可见；
  左侧深色条用渐变画在网格上，所以页面再长也不会在侧边栏下方露出浅色缝隙。
- 要改高度只改 `--page-min-height` 这一个变量（例如固定 `1920px`）。

实测 1440×900、2560×1440、768×1024、390×844、320×568 五种尺寸均正常。

## 部署到服务器

干净的 Debian / Ubuntu 服务器，一条命令装完——Node、运行用户、systemd 服务、
Nginx 反向代理、HTTPS 证书、管理员账号：

```bash
# 网站代码在 claude/adoring-shannon-88sms1 分支上，clone 时要带 -b
git clone -b claude/adoring-shannon-88sms1 \
  https://github.com/Esko-zhang/agent.git && cd agent/website

sudo DOMAIN=catalogue.你们的域名 WITH_TLS=1 TLS_EMAIL=you@yourdomain.com \
     bash deploy/install.sh
```

细节、参数、日常运维和排错都在 **[`deploy/README.md`](deploy/README.md)**。要点：

- 脚本可重复执行：**不覆盖 `.env`、不动数据库、不重置已有管理员**，`git pull` 后再跑一次即可；
- 应用只监听 `127.0.0.1`，外网一律走 Nginx，安全组**只放行 80 / 443 和 SSH**；
- `deploy/update.sh` 更新（先自动备份），`deploy/backup.sh` 备份数据库 + 图片 + 文档；
- 服务器在**中国大陆**且域名**未备案**的话，80 端口会被拦截。这个站是发给海外客户的，
  **香港 / 新加坡地域更合适**：不用备案，客户访问也更快。

两个最容易踩的坑：

> **没有 HTTPS 就别开 `COOKIE_SECURE=1`。** 带 Secure 的 Cookie 在 HTTP 下浏览器不回传，
> 表现是密码输对了也一直弹回登录页。脚本在没配证书时会自动设成 0，证书装好后记得改回 1。

> **走代理必须设 `TRUST_PROXY=1`。** 否则登录限流会把所有访客当成同一个 IP，
> 访问记录里的 IP 和国家也全是 Nginx 自己的。

## 环境变量

见 [`.env.example`](.env.example)。关键项：

| 变量 | 说明 |
|---|---|
| `SESSION_SECRET` | **必改**，签名会话 Cookie；生产环境少于 32 位会直接拒绝启动 |
| `NODE_ENV` | 生产环境设为 `production` |
| `TRUST_PROXY` | 信任几层代理，直接决定访问记录里的 IP 是否正确，见上文 |
| `COOKIE_SECURE` | 仅经 HTTPS 发送会话 Cookie（`production` 下默认开启） |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | 仅 `npm run init-db` 首次建号时使用 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` | 发信服务器；阿里云企业邮箱为 `smtp.qiye.aliyun.com` / `465` / `1` |
| `SMTP_USER` / `SMTP_PASS` | 完整邮箱地址 + 三方客户端安全密码；留空即关闭邮件通知 |
| `SMTP_FROM` | 收件人看到的发件人，必须与 `SMTP_USER` 同一地址 |
| `INQUIRY_NOTIFY_TO` | 除业务员名片邮箱外额外的收件人，逗号分隔 |
| `MAX_UPLOAD_MB` | 单张图片上限，默认 5 |
| `SESSION_TTL_HOURS` | 登录有效期，默认 12 小时 |
| `LOGIN_MAX_ATTEMPTS` / `LOGIN_WINDOW_MINUTES` | 登录失败限流，默认 15 分钟内 8 次 |

## 安全设计

- 密码 bcrypt（cost 12）哈希存储
- 会话 Cookie `HttpOnly` + `SameSite=Lax` + HMAC-SHA256 签名；生产环境 `Secure`
- 全站写操作校验 CSRF Token；上传接口在解析 multipart 后补验，二者绑定在同一个中间件里，无法漏配
- 登录失败按 IP + 账号限流
- 无注册路由；账号停用后，已签发的会话下次请求立即失效
- 上传限 JPG/PNG/WebP/GIF + 体积上限 + 随机重命名
- CSP 禁止内联脚本与样式；`X-Frame-Options: DENY`、`nosniff`
- 管理员不能停用/降级/删除自己，且系统始终保留至少一个启用的管理员

## 定位：私密站点，不做 SEO

这个站是**发给指定客户看的**，不追求自然流量。因此：

- 整站登录才能访问，账号只能由管理员在后台创建，前台没有注册入口；
- 每个页面都带 `noindex, nofollow`，并且 `robots.txt` 整站 `Disallow`；
- 不需要、也不应该为了搜索引擎把产品列表公开。

> 如果以后改主意要做自然流量，需要改成「产品列表公开、规格数据登录可见」的两层结构，
> 那是另一个产品形态，不要顺手改——会把现在的私密性弄没。
